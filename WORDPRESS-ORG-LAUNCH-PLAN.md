# AutoloadFix WordPress.org Launch Plan

## Permanent slug strategy

**Target slug:** `autoloadfix`

Submit the first WordPress.org package while the main plugin header remains `Plugin Name: AutoloadFix`. WordPress.org generates the initial slug from the Plugin Name. Once approved, keep the slug permanently and do not submit a replacement plugin only to chase a different URL.

After the slug is locked, the public display name can be made more descriptive without changing the permalink. Recommended post-approval display name:

**AutoloadFix – Performance & Cache Toolkit**

## Search positioning

Primary intent:
- WordPress performance
- cache diagnostics
- database/autoload optimization
- autoloaded options
- Site Health

Readme tags for the initial listing:
1. performance
2. cache
3. database
4. autoload
5. site health

Short description:

> Audit autoloaded options, diagnose database and cache issues, scan slow pages, and verify WordPress performance fixes safely.

The description should use these phrases naturally. Do not keyword-stuff, repeat competitor names as tags, or make guaranteed speed/ranking claims.

## Listing conversion plan

Before the first public SVN release, prepare unique WordPress.org assets:
- 256x256 and 128x128 plugin icon
- 1544x500 and 772x250 banner
- 8–12 real screenshots matching the readme screenshot captions
- screenshot 1 should show the Autoload Health overview
- screenshot 2 should show Monitor & Tools
- screenshot 3 should show Cache & Optimization Advisor
- screenshot 4 should show Site Problem Scanner with page-level results
- screenshot 5 should show a problem's guided fix steps
- screenshot 6 should show Optimization Profiles / safe-change state

Use a consistent AutoloadFix/WP Zenora visual identity. Do not use unmodified third-party product logos as the plugin identity.

## First 30 days after approval

### Day 0–2
- Commit the approved production package to WordPress.org SVN.
- Verify the public plugin page, download, screenshots, icon, banner, changelog, and contributor profile.
- Test a clean install from WordPress.org, not only the local ZIP.

### Week 1
- Subscribe to the plugin support forum.
- Reply quickly to genuine support questions.
- Fix reproducible compatibility issues with small, well-documented releases.
- Keep `Tested up to` current when a new WordPress release has actually been tested.

### Week 2–4
- Improve the readme based on real user questions.
- Add FAQ entries for recurring issues.
- Publish meaningful updates only; do not release empty updates for ranking purposes.
- Ask satisfied users for an honest review only after they have received value; never incentivize or fabricate reviews.

## Ongoing ranking/discovery principles

WordPress.org search cannot be guaranteed. Sustainable discovery comes from:
- a clear, useful readme in the user's language,
- genuine installs and retention,
- prompt support,
- good authentic reviews,
- current compatibility metadata,
- reliable releases,
- low-friction onboarding,
- screenshots that explain the value quickly.

Track these product metrics manually after launch:
- active installs
- support topics opened/resolved
- average review score and review themes
- recurring setup failures
- compatibility reports
- which features users mention most often

Use those signals to improve the plugin rather than changing the slug or stuffing keywords.
